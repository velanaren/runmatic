# Sprint 14 — Pods & Deployments — Notes

## Phase 1 — The Hook

**Claude's Explanation:** A Pod is the smallest unit K8s runs — one or more containers with shared network and storage. But a bare Pod has no owner: if it crashes, it stays dead. A Deployment is the contract: "I want 2 of these, always." The Deployment controller watches reality against the spec and acts on every gap — same as Autosys's master daemon watching job definitions vs running instances.

**First Test:** Run a bare pod, delete it, observe it doesn't come back.
```bash
kubectl run orphan --image=nginx --restart=Never
kubectl delete pod orphan
kubectl get pods
# Result: No resources found in default namespace
```

**My Result:** Pod deleted, gone permanently. No recovery. Established why Deployments exist before writing a single line of YAML.

## Phase 3 — The Challenge

**Claude's Challenge:** Trigger a rolling update to a non-existent image. Diagnose what happens. Roll back without editing YAML.

**My Investigation:**

Before triggering, checked rolling update strategy:
- replicas: 2, maxSurge: 25% (rounds up to 1), maxUnavailable: 25% (rounds down to 0)
- Predicted: 1 new pod created, 0 old pods removed until new pod is healthy, max 3 pods total

```bash
kubectl set image deployment/runmatic-api api=runmatic-api:does-not-exist
kubectl get pods -w -l app=runmatic-api
```

Observed:
- New pod `668f75fb48-d2cq8` created → `ErrImageNeverPull` immediately
- Old 2 pods stayed Running (maxUnavailable: 0 protected them)
- New pod never became healthy → rollout stalled
- `kubectl rollout status` showed: "Waiting for deployment... 1 out of 2 new replicas have been updated"

After 10 minutes:
- `progressDeadlineExceeded` error surfaced in `rollout status`
- New pod went to Terminating after `rollout undo` (not automatically — manual action required)

Fix:
```bash
kubectl rollout undo deployment/runmatic-api
kubectl rollout status deployment/runmatic-api
# deployment "runmatic-api" successfully rolled out
```

Same 2 original pods still Running — `rollout undo` scaled old ReplicaSet back to 2, new RS to 0.

## Phase 4 — Explanation

**Claude's Question:** Explain Deployment vs bare container to a support engineer in 3 sentences.

**My Answer:** "Deployment is like a contract, telling Kubernetes these are my desired state and maintain it automatically. So if a pod goes down or node goes down, Kubernetes continuously monitors the desired state and actual state and ensures the desired state is maintained. If it is not a deployment, the desired state will not be maintained, if a pod goes down it is gone forever — there is no contract to maintain it."

**Claude's Feedback:**
- "Contract for desired state" — precise framing ✅
- Reconciliation loop — correctly described ✅
- Both failure modes named (pod crash, node failure) ✅
- Gap: didn't name ReplicaSet as the intermediate layer (Deployment → ReplicaSet → Pods)
- Gap: no readiness/liveness probes in manifest

## Key Takeaways

1. **Pod vs Deployment**: A bare Pod has no owner. When it dies, it stays dead. A Deployment owns a ReplicaSet which owns pods — deletion of a pod triggers immediate replacement.

2. **Three-layer hierarchy**: Deployment → ReplicaSet → Pods. The Deployment manages ReplicaSets; the ReplicaSet manages pods. `kubectl get rs` shows the intermediate layer.

3. **pod-template-hash**: Auto-generated by K8s for each unique pod template. Every image change or config change = new hash = new ReplicaSet. Old ReplicaSets stay at 0 replicas (not deleted) — that's how `rollout undo` works.

4. **maxSurge / maxUnavailable math**: With replicas=2, maxSurge=25% (→1), maxUnavailable=25% (→0): during a rolling update, min 2 pods always Running, max 3 pods total. Old pods only removed after new pods are Ready.

5. **progressDeadlineExceeded**: If new pods never become Ready within `progressDeadlineSeconds` (default 600s), K8s marks the Deployment as degraded. It does NOT auto-rollback. Manual `rollout undo` required.

6. **rollout undo mechanism**: Scales the previous ReplicaSet back to desired replicas, scales the failed ReplicaSet to 0. No new pods created — the old ones were dormant, not gone.
